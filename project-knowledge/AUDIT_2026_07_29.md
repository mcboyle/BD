## Tier 1  --  will break a capture or corrupt operator state

### 1. `tests/test_e2e_smoke.py` writes a permanent site into the operator's real `sites_config.json` on every suite run
The only finding here that mutates production state rather than misreporting it.

`bulk_downloader/app.py:1167` is `SITES_FILE = Path("sites_config.json")`  --  CWD-relative, and `BD_INSTALL_DIR` does not govern it. `_RealE2ESmoke.setUpClass` POSTs `/api/sites` to create "E2E Test Site"; `tearDownClass` never deletes it. The harness isolates `BD_INSTALL_DIR` and the SQLite DB into a temp dir, but the site config escapes into the pytest CWD  --  the operator's install root.

`[re-derived]` This sandbox's untracked `sites_config.json` holds **7** entries, all named `E2E Test Site`. An earlier verdict tonight measured 4. It gained 3 during this audit. The leak is incrementing while you read this.

Downstream: every site-count denominator in the bundle is inflated (`selftest: 7 site(s), all structurally valid`; L8's "9 site(s) configured"), and at >=4 sites the SPA collapses idle sites by default, so it changes the operator's UI. Not a regression from tonight  --  the previous capture shows the identical 5 -> 6 step and verdicted PASS.

Fix: resolve `SITES_FILE` against `BD_INSTALL_DIR` (real fix, touches `app.py`), or delete the site in `tearDownClass` (band-aid, test-only, available immediately).

### 2. L34 budgets 72s inside a 60s wall  --  false `TIMEOUT ... thread leaked` FAIL on every non-capture.sh run
`[re-derived]` `harness.DEFAULT_PER_CHECK_TIMEOUT_S = 60.0`; `checks._L34_WALL_S = 72.0`. `capture.sh:865` passes `--per-check-timeout 90`, so captures are safe. `tools/install_livecheck_timer.sh:65` hardcodes `PER_CHECK_TIMEOUT="60"` and line 152 writes it into `bd-livecheck.service`.

If that timer is installed on test4, L34 FAILs on every unattended fire, forever, on a healthy app  --  and its only output channel is journalctl. Verified by execution against a fixture where every operator route answered in 10ms: 60s wall  ->  `FAIL TIMEOUT`, 90s wall  ->  `PASS`.

Compounding: L34's runtime is not a function of app health. Its advisory diagnostic pass deliberately spends the remaining wall down to ~66-71s whenever the `/api/dev` + `/cockpit` surface exceeds the leftover budget. It is *built* to approach the wall.

Fix: pass the harness's actual `per_check_timeout_s` into `Context`, derive `_L34_WALL_S` from it (e.g. 0.8x), and add one test asserting derived < supplied. Bumping the timer to 90 is the one-line stopgap. Right now the safety property is a comment asserting a harness fact, and every test for it monkeypatches the constant away.

### 8. L8 and L9 both PASS on a jar containing zero cookies
L8's only content test is `size == 0`. L9 computes `n_cookies` and uses it solely in log strings. Verified PASS on `{}`, `[]`, `{"cookies": []}` and Playwright's real `{"cookies": [], "origins": []}` storage_state shape. These are the only two of 37 checks that read a cookie jar, and their result feeds the capture verdict  --  so together they certify "authentication persists" over a jar with no auth cookie.

The shape is producible: `save_cookies_to_file(path, [])` succeeds (round-trip validation compares 0 to 0), and `session_keeper._persist_cookies` calls it unguarded, so one heartbeat on a logged-out context overwrites a good jar with 2 bytes that both checks then bless.

**Do not just add `n > 0`.** The parser returns `(True, 'json-other-shape', 0)` for the legacy dict-of-domain jar that `cookies._verify_cookie_roundtrip` explicitly accepts  --  an `n > 0` gate would false-FAIL a valid jar. Teach the parser that shape first. The identical `st_size == 0` blind spot exists at `cookie_health.py:206`, which drives the nightly auth-health job.

Adjacent to known defect C  --  same subsystem, opposite direction. C is a false negative on `auth_state`; this is a false positive on cookie persistence. Worth handing to whoever owns C.
